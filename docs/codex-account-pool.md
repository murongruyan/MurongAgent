# Codex 多账号池

MurongAgent 的 Codex 多账号池用于在额度不足时安全地继续下一轮任务，不用于并发共享账号，也不会在任务执行途中更换身份。

## 切换边界

1. 新一轮任务开始前刷新当前账号的登录与额度。
2. 当前账号可用且高于保留阈值时保持不变。
3. 当前账号低额度时，按可用额度、冷却状态和最近使用时间选择候选账号。
4. 停止旧账号的官方 Codex app-server，激活候选账号并重新验证登录与额度。
5. 为当前 Murong 会话绑定新账号，并以已有 Murong 聊天记录重建新的官方 Codex 线程。

切换不会发生在模型流式输出、工具调用、文件写入或上传过程中。锁定的会话始终使用其绑定账号，即使该账号额度较低也不会自动切换。

## 隔离与凭据

- 默认账号沿用原有 `codex-home`，升级后无需重新登录。
- 后续账号使用 `codex-accounts/<account-id>`，各自隔离官方线程、运行时状态和登录文件。
- Windows 非活动账号的 `auth.json` 使用当前 Windows 用户的 DPAPI 加密。
- macOS / Linux 非活动账号的 `auth.json` 使用应用私有 AES-256-GCM 密钥加密。
- Android 非活动账号的 `auth.json` 使用 Android Keystore 中的设备密钥进行 AES-GCM 加密。
- 账号轮换时先原子保存加密副本，成功后才删除旧账号明文；只有活动账号会物化明文供官方 app-server 读取。
- 新版官方 app-server 可能只在各账号自己的私有状态数据库中保存认证而不生成 `auth.json`；此时已验证的账户快照会作为持久登录标记，账号目录仍保持隔离。

账号池元数据位于应用私有数据目录。普通跨平台备份、聊天导出和日志不会包含账号池凭据。只有用户在已配对设备上明确确认“设备同步”时，完整 Codex/GitHub 账号池才会在现有 AES-256-GCM 通道中短暂解密传输；接收端按账号身份合并后立即使用本机 DPAPI 或 Android Keystore 重新加密，任一步失败都会恢复导入前状态。

## 额度策略

默认保留阈值为 10%，失败冷却为 15 分钟。存在多个滚动额度窗口时，以剩余比例最低的窗口作为账号得分，避免某个短窗口已经耗尽却仍被误选。

候选账号必须同时满足：

- 已启用；
- 不在失败冷却期；
- 有已验证账户快照、可解密凭据或当前活动登录文件；
- 官方 app-server 能确认已登录；
- 实时额度高于保留阈值。

若所有候选账号均不可用，系统保留原账号（只要其仍能登录）并向用户说明原因，不会在账号之间无限循环。

## 双端登录持久化

Android 没有 Linux Secret Service；桌面平台的系统 keyring 行为也会因环境不同而变化。因此双端启动每个官方 app-server 前都会在该账号的 `config.toml` 固定 `cli_auth_credentials_store = "file"`，避免设备码登录只存在于当前进程或落入非隔离的系统存储。官方生成 `auth.json` 时，明文仅属于活动账号；切换时由 Android Keystore、Windows DPAPI 或桌面私有 AES-GCM 密钥加密并移除。

`account/read` 暂时返回空账户（例如 app-server 重启或网络刷新失败）不会删除已保存账号；界面显示待验证状态。只有用户明确退出登录才清理凭据和账号元数据。
